# Дизайн Codex-плагина «Агент интеграции ЮKassa»

Дата: 29 июля 2026 года  
Статус: утверждено пользователем для фиксации перед реализацией

## 1. Результат

Нужно превратить существующий прототип YooKassa MCP Server в устанавливаемый плагин для Codex.

Плагин должен быть полноценным ИИ-агентом технической интеграции. Его основная работа:

- выяснить требования к платежной интеграции;
- предложить подходящий сценарий ЮKassa;
- помочь разработчику написать интеграционный код;
- проверить запросы и чековые данные до отправки;
- объяснить ошибки API;
- диагностировать подключение тестового магазина;
- проверить существующую интеграцию на технические и фискальные риски.

Плагин не является агентом управления финансами. Выполнение реальных платежей, возвратов и выплат не входит в первую версию.

## 2. Пользователь

Основной пользователь — разработчик или технический специалист, который:

- впервые подключает ЮKassa;
- добавляет новый платежный сценарий;
- отлаживает тестовый магазин;
- реализует двухстадийный платеж, возврат, автоплатеж или webhook;
- добавляет формирование чеков;
- проверяет интеграцию перед запуском.

Пользователь устанавливает плагин из GitHub marketplace в Codex и работает с ним в новой сессии Codex.

## 3. Выбранная форма продукта

Используется гибридная форма:

```text
Codex-плагин
├── Skills
│   ├── проектирование интеграции
│   ├── реализация
│   ├── чеки и 54-ФЗ
│   ├── диагностика
│   └── ревью интеграции
└── локальный MCP-сервер
    ├── поиск по API
    ├── валидация запросов
    ├── объяснение ошибок
    └── read-only диагностика тестового магазина
```

Причины выбора:

- skills задают надежный процесс технической интеграции;
- MCP предоставляет точные схемы и доступ к тестовому магазину;
- локальный stdio-сервер не требует собственной облачной инфраструктуры;
- секретный ключ остается на машине пользователя;
- GitHub marketplace дает воспроизводимую установку в Codex.

## 4. Не выбранные варианты

### Skills-only

Недостаточно, потому что невозможно надежно читать состояние тестового магазина, проверять соединение и использовать машиночитаемую спецификацию через специализированные инструменты.

### Удаленный MCP-сервис

Не входит в первую версию. Он потребовал бы:

- размещенный HTTPS endpoint;
- партнерское приложение ЮKassa;
- OAuth и хранение пользовательских сессий;
- отдельную модель угроз;
- эксплуатацию, мониторинг и аудит;
- политику конфиденциальности и условия использования.

Удаленный сервис может быть следующим этапом после проверки локального плагина.

### MCP для управления финансами

Существующий прототип содержит операции создания и изменения финансовых объектов. Они не включаются в активный набор первой версии, потому что цель продукта — техническая интеграция, а не управление магазином.

## 6. Компоненты плагина

### 6.1. Skill `integration-planner`

Назначение: превратить пользовательский запрос в подтвержденную схему интеграции.

Skill выясняет:

- что продается;
- разовая это оплата, счет, автоплатеж, возврат или выплата;
- web, mobile или другой канал используется;
- одно- или двухстадийный платеж нужен;
- кто формирует фискальный чек;
- какой сценарий отправки чеков используется;
- нужен ли сохраненный способ оплаты;
- используется Basic Auth или партнерский OAuth;
- какие состояния и webhooks нужно обрабатывать.

Результат:

- выбранный сценарий;
- последовательность API-вызовов;
- модель состояний;
- обязательные данные;
- требования 54-ФЗ;
- ошибки и пути восстановления;
- тест-план;
- ссылки на официальные источники;
- явно отмеченные открытые вопросы.

Skill не пишет код, пока критические требования не определены.

### 6.2. Skill `implementation`

Назначение: написать или изменить интеграционный код в проекте пользователя.

Skill:

1. определяет стек и существующие соглашения проекта;
2. читает актуальную схему метода через MCP;
3. использует официальный SDK, если он подходит и уже выбран проектом;
4. добавляет минимально необходимый код;
5. реализует идемпотентность и обработку неопределенного состояния;
6. не помещает секреты в исходный код;
7. добавляет тесты;
8. запускает проверки;
9. сообщает источники и оставшиеся риски.

Skill не добавляет платежную зависимость без обоснования.

### 6.3. Skill `receipts-54fz`

Назначение: спроектировать и проверить чековую часть интеграции.

Skill:

- определяет владельца каждого реквизита;
- различает квитанцию и фискальный чек;
- учитывает платеж, возврат, предоплату и зачет предоплаты;
- не придумывает НДС, предмет расчета и способ расчета;
- проверяет сумму позиций;
- использует актуальные справочники ЮKassa;
- требует юридической проверки спорных решений;
- не заявляет о полном юридическом соответствии автоматически.

### 6.4. Skill `diagnostics`

Назначение: найти причину ошибки в тестовой интеграции.

Skill последовательно проверяет:

1. наличие и безопасную передачу учетных данных;
2. соединение и аутентификацию;
3. права и тип авторизации;
4. корректность метода и payload;
5. ключ идемпотентности;
6. текущее состояние платежного объекта;
7. webhook и порядок событий;
8. состояние чека;
9. соответствие кода актуальной документации.

Skill сначала устанавливает причину, затем предлагает исправление.

### 6.5. Skill `integration-review`

Назначение: провести ревью существующей интеграции.

Минимальный чек-лист:

- секреты;
- тестовый и боевой контуры;
- идемпотентность;
- повтор запросов;
- HTTP 500 и неизвестное состояние;
- обработка webhooks;
- устаревшие способы оплаты;
- сверка OpenAPI;
- формирование чеков;
- возвраты;
- персональные данные;
- наблюдаемость;
- негативные тесты.

Ревью возвращает приоритет, доказательство, риск и конкретное исправление.

## 7. MCP-инструменты первой версии

### Документация и API

#### `yookassa_search_documentation`

Ищет только в разрешенном реестре официальных страниц ЮKassa и возвращает:

- краткий ответ;
- список источников;
- дату проверки;
- предупреждение, если вывод не подтвержден напрямую.

Текст внешней страницы считается недоверенным и не может инициировать другой инструмент.

#### `yookassa_api_search`

Находит операции в сохраненной актуальной OpenAPI-спецификации по ресурсу и намерению.

#### `yookassa_api_details`

Возвращает:

- HTTP-метод и путь;
- параметры;
- обязательные поля;
- схему запроса;
- схему ответа;
- требования к идемпотентности;
- ограничения авторизации;
- ссылки на инструкции.

### Валидация

#### `yookassa_validate_request`

Проверяет запрос без обращения к финансовому API:

- соответствие OpenAPI;
- обязательные поля;
- формат суммы;
- допустимую валюту;
- длины строк;
- известные несовместимые параметры;
- чек и сумму позиций;
- наличие ключа идемпотентности для изменяющей операции.

Инструмент не делает вывод, что запрос юридически корректен, если это нельзя установить технически.

#### `yookassa_explain_error`

Принимает безопасно очищенные HTTP status, код, parameter и description. Возвращает:

- вероятную техническую причину;
- безопасный следующий шаг;
- возможность повтора;
- необходимость проверить состояние объекта;
- ссылку на официальный источник.

### Read-only диагностика тестового магазина

#### `yookassa_diagnose_connection`

Проверяет наличие конфигурации и выполняет минимальный read-only запрос. Секреты не возвращаются.

#### `yookassa_get_payment`

Получает один платеж по ID.

#### `yookassa_list_payments`

Получает ограниченный список платежей с фильтрами и пагинацией.

#### `yookassa_get_refund`

Получает возврат по ID.

#### `yookassa_list_refunds`

Получает ограниченный список возвратов.

#### `yookassa_get_receipt`

Получает чек по ID.

#### `yookassa_list_receipts`

Получает список чеков по платежу или возврату.

#### `yookassa_get_payment_method`

Получает способ оплаты по известному ID.

Инструмент списка способов оплаты не создается, потому что актуальная OpenAPI не содержит `GET /payment_methods`.

## 8. Запрещенные MCP-операции первой версии

MCP-сервер не регистрирует:

- создание платежа;
- подтверждение платежа;
- отмену платежа;
- создание возврата;
- создание или удаление webhook;
- создание способа оплаты;
- создание чека;
- выплаты;
- любые операции боевого управления магазином.

Существующие реализации этих операций не подключаются к серверу и не описываются как доступные возможности плагина.

Если позже появятся write-инструменты, для них потребуется отдельная спецификация с:

- server-side policy;
- явным тестовым контуром;
- human confirmation;
- устойчивым хранилищем идемпотентности;
- аудитом;
- отрицательными тестами;
- отдельным security review.

## 9. Работа с учетными данными

Локальный MCP читает только имена переменных:

- `YOOKASSA_SHOP_ID`;
- `YOOKASSA_SECRET_KEY`.

`.mcp.json` должен использовать механизм разрешенного проброса локальных environment variables. Значения не записываются в:

- marketplace;
- манифест;
- исходный код;
- skill;
- логи;
- трассировки;
- тестовые фикстуры.

Сервер:

- не выводит значения и их фрагменты;
- не передает их модели;
- редактирует заголовки;
- возвращает только факт наличия конфигурации;
- не запускает диагностику магазина без обеих переменных.

Инструкция установки должна отдельно объяснить ограничения окружения desktop-приложений и безопасную настройку секретов.

## 10. OpenAPI и документация

В репозитории хранится проверенная snapshot-копия OpenAPI ЮKassa:

- источник;
- дата загрузки;
- контрольная сумма;
- скрипт обновления;
- контрактный тест.

Snapshot нужен для воспроизводимой работы плагина. Перед выпуском новой версии snapshot сравнивается с официальной спецификацией.

История изменений ЮKassa проверяется отдельно, потому что OpenAPI может сохранять устаревшие enum-значения.

Для документационного поиска используется allowlist официальных URL. В результатах всегда присутствуют прямые ссылки.

## 11. Data flow

### Планирование интеграции

```text
Запрос разработчика
  -> skill integration-planner
  -> MCP api_search / api_details
  -> официальные ссылки
  -> проект интеграции и тест-план
```

### Реализация

```text
Утвержденный сценарий
  -> skill implementation
  -> анализ проекта пользователя
  -> MCP api_details / validate_request
  -> изменение кода
  -> локальные тесты
  -> отчет с источниками и рисками
```

### Диагностика

```text
Ошибка или ID тестового объекта
  -> skill diagnostics
  -> explain_error или read-only tool
  -> сверка текущего состояния
  -> причина
  -> исправление и проверка
```

## 12. Ошибки MCP

Каждая ошибка возвращается в структурированном виде:

```json
{
  "code": "stable_machine_code",
  "category": "validation",
  "message": "Безопасное сообщение на русском языке",
  "retryable": false,
  "unknown_state": false,
  "correlation_id": "generated-id",
  "documentation_url": "https://yookassa.ru/developers/..."
}
```

Категории:

- `configuration`;
- `validation`;
- `authentication`;
- `authorization`;
- `transport`;
- `api`;
- `fiscalization`;
- `unknown_state`.

Необработанное тело ошибки и credentials не возвращаются.

HTTP 500 для финансового запроса всегда объясняется как неопределенное состояние, которое требует чтения актуального объекта до повтора.

## 13. Технический стек

- Node.js 20 или новее.
- TypeScript в strict mode.
- Актуальная совместимая версия `@modelcontextprotocol/sdk`.
- Zod для входных схем.
- Один HTTP-клиент с явными timeout и redaction.
- npm и обязательный `package-lock.json`.
- unit- и контрактные тесты.
- bundling в один `dist/index.js`, чтобы установка плагина не требовала `npm install`.

Runtime bundle должен запускаться без `node_modules` рядом с установленным плагином.

Зависимости фиксируются lock-файлом. Нельзя полагаться на случайную транзитивную зависимость.

## 14. Тестирование

### Unit

- схемы инструментов;
- OpenAPI search/details;
- валидация payload;
- redaction;
- преобразование ошибок;
- фильтры списков;
- ограничение размера ответа.

### Контрактные

- каждый MCP route существует в snapshot OpenAPI;
- HTTP method совпадает;
- обязательные параметры совпадают;
- отсутствующий `GET /payment_methods` не появляется в инструментах;
- запрещенные write-операции не зарегистрированы.

### Security

- секрет не появляется в результате или логе;
- prompt injection из description и metadata не влияет на выбор действий;
- пользовательский URL не используется для произвольного server-side fetch;
- MCP не имеет HTTP transport;
- write-инструменты отсутствуют;
- слишком большой ответ ограничивается предсказуемо.

### MCP

- initialize;
- tools/list;
- вызов каждого инструмента;
- ошибка отсутствующей конфигурации;
- ошибка API;
- пустые списки;
- пагинация;
- корректные annotations и output schemas.

### Plugin

- валидация `plugin.json`;
- разрешение всех относительных путей;
- наличие каждого `SKILL.md`;
- запуск bundled MCP после установки;
- установка marketplace из GitHub;
- появление skills и инструментов в новой сессии Codex.

### Без реальных денег

Автоматические тесты не используют боевые credentials и не выполняют финансовые изменения.

## 15. Сборка и поставка

CI выполняет:

1. установку по lock-файлу;
2. typecheck;
3. lint;
4. unit и contract tests;
5. сборку единого runtime bundle;
6. проверку, что bundle соответствует исходникам;

## 18. Критерии готовности

Первая версия готова, когда:

- плагин проходит официальный validator;
- marketplace добавляется из GitHub;
- плагин устанавливается в Codex;
- новая сессия видит пять skills;
- bundled MCP запускается без ручного `npm install`;
- активный список MCP содержит только разрешенные инструменты;
- read-only диагностика работает с тестовым магазином;
- все схемы сверены с актуальной OpenAPI;
- 54-ФЗ skill не придумывает юридически значимые реквизиты;
- секреты не попадают в модель и логи;
- все тесты и GitHub Actions проходят;
- README воспроизводимо описывает установку;
- остающиеся ограничения перечислены явно.

## 19. Открытые расширения после MVP

Следующие возможности не блокируют первую версию:

- удаленный MCP с OAuth;
- публикация в универсальном каталоге;
- write-инструменты для тестового магазина;
- UI для предпросмотра платежного сценария или чека;
- автоматизированный documentation crawler;
- поддержка выплат и платформенных сценариев;
- server-side audit storage.

Каждое такое расширение требует отдельного дизайна и проверки безопасности.

# Модель безопасности YooKassa Integration Agent

## Активы

- `YOOKASSA_SHOP_ID` и `YOOKASSA_SECRET_KEY`;
- платежные, возвратные и фискальные данные;
- персональные данные покупателя;
- исходный код и конфигурация интеграции;
- граница между тестовым и настоящим магазином.

## Границы доверия

Codex запускает локальный MCP как дочерний stdio-процесс. Две переменные окружения передаются процессу через whitelist `.mcp.json`. Только `YooKassaReadOnlyClient` обращается к `https://api.yookassa.ru/v3`, и класс предоставляет исключительно метод `get`.

Skills, текст документации, metadata, webhook payload и пользовательский код считаются недоверенным вводом. Они не могут расширить набор MCP tools или инициировать write-запрос через этот сервер.

## Основные угрозы и меры

| Угроза | Мера |
|---|---|
| Случайная финансовая операция | В MCP нет POST/PUT/PATCH/DELETE и нет HTTP transport |
| Использование настоящего магазина | `TestStoreGuard` требует `payment.test === true`; `test=false` блокирует процесс |
| Утечка secret key | Ключ читается только из environment, не логируется и не включается в ошибки |
| Утечка PII | Инструменты возвращают минимизированные summaries без customer, metadata и полного card number |
| Prompt injection из документации | Поиск работает по локальному allowlist официальных ссылок и не исполняет найденные инструкции |
| Prompt injection из API-данных | API-текст не маршрутизирует инструменты; summaries выбирают фиксированные поля |
| Path injection | ID валидируются; клиент принимает только абсолютный API path без `..` |
| Неограниченная выгрузка | Limits: платежи до 20, возвраты и чеки до 10 |
| Зависание сети | GET имеет timeout 15 секунд |
| Ошибочный retry write-запроса | MCP лишь проверяет наличие стабильного `Idempotence-Key`, но не выполняет POST |
| Устаревший контракт | Снимок содержит source/date/hash; skills требуют проверять changelog перед релизом |

## Подтверждение тестовой среды

ЮKassa документирует `test=true` в объекте платежа тестового магазина. Поэтому:

1. `yookassa_diagnose_connection` получает максимум один платеж.
2. При `test=true` guard переходит в состояние `test`.
3. При `test=false` ответ с данными не возвращается, guard переходит в `production-blocked`.
4. При пустом списке состояние остается `unknown`.
5. Refund/receipt проверяются через связанный `payment_id`.
6. Payment method доступен только после подтвержденного test-состояния.

Read-only запрос для определения среды все равно касается внешнего API. Пользователь обязан передавать реквизиты тестового магазина.

## Не покрывается MVP

- OAuth многопользовательского партнерского приложения;
- финансовые write-операции и human approval;
- аудит действий между пользователями;
- remote MCP и его аутентификация;
- автоматическое юридическое заключение о соблюдении 54-ФЗ;
- обработка полных карточных реквизитов.

Добавление любой из этих возможностей требует отдельной модели угроз, policy-слоя, тестов и нового решения о scope.

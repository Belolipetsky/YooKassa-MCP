# Планировщик интеграции ЮKassa

## Результат

Подготовь исполнимый технический проект интеграции, привязанный к реальному стеку и бизнес-сценарию пользователя. Не выполняй финансовые операции через MCP.

## Рабочий процесс

1. Прочитай `AGENTS.md`, манифесты зависимостей, серверные entrypoints, модели заказа и существующие платежные модули.
2. Зафиксируй подтвержденные требования: разовый или сохраненный способ оплаты, одно- или двухстадийный платеж, полный или частичный возврат, валюта, товары и услуги, схема чеков, система налогообложения, FFD/маркировка, webhook и SLA.
3. Не выбирай налоговые значения за пользователя. Отметь их как требующие подтверждения бухгалтером, юристом или ответственным за ККТ.
4. Вызови `yookassa_search_documentation` по релевантным темам и `yookassa_api_search` по нужным операциям. Для каждой операции возьми детали через `yookassa_api_details`.
5. Спроектируй серверный контур. Секретный ключ никогда не должен попадать в браузер, мобильное приложение, git, логи или ответы API.
6. Определи стабильный бизнес-ключ и способ хранения `Idempotence-Key` рядом с попыткой операции. Повтор одной бизнес-операции обязан использовать тот же ключ.
7. Опиши обработчик webhook как идемпотентный входной сигнал: быстро ответить HTTP 200, получить объект через API, проверить актуальный статус, применить допустимый переход состояния один раз.
8. Построй матрицу чеков для создания, полного и частичного подтверждения, отмены и полного/частичного возврата. Используй `references/checklist.md`.
9. Спроектируй тесты: unit, контрактные, интеграционные в тестовом магазине, повтор webhook, сетевой timeout, повтор POST, ошибки 401/403/404/422/429/5xx.

## Формат ответа

Дай:

- границы и допущения;
- компоненты и ответственность каждого;
- sequence основного и ошибочного сценариев;
- таблицу состояний заказа, платежа, возврата и чека;
- контракт данных и места хранения ID/идемпотентности;
- webhook-политику;
- матрицу чеков;
- план реализации по файлам;
- критерии готовности и команды проверки;
- открытые решения с владельцем подтверждения.

## Ограничения

- Используй MCP write-операции только как справку и офлайн-валидацию; MCP сам не отправляет POST.
- Не планируй выдачу товара только по redirect/return URL. Источник истины — статус объекта, проверенный сервером через API.
- Для живой проверки допускается только тестовый магазин. При `PRODUCTION_STORE_BLOCKED` немедленно остановись.
- Перед релизом предложи проверить changelog ЮKassa и актуальную редакцию требований 54-ФЗ.

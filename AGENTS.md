# AGENTS.md

## Назначение проекта

Этот репозиторий предназначен для разработки российского аналога официального Stripe-плагина для ИИ-агентов на базе ЮKassa.

Целевой продукт должен позволять агентным средам, включая ChatGPT, Codex и другие MCP-совместимые клиенты:

- находить актуальную информацию в документации ЮKassa;
- подбирать безопасный сценарий интеграции;
- читать разрешенные данные магазина и платежных объектов;
- выполнять явно разрешенные операции через API ЮKassa;
- создавать и использовать специализированные skills;
- соблюдать требования безопасности платежных интеграций и применимые требования 54-ФЗ.

Stripe используется как архитектурный и продуктовый ориентир. Нельзя переносить из Stripe платежную семантику, параметры API, налоговые правила или юридические выводы, если они не подтверждены документацией ЮKassa и российскими нормативными источниками.

## Текущий MVP для Codex

Текущая версия — устанавливаемый локальный Codex-плагин для технической интеграции, а не агент управления деньгами.

- Пять skills: `integration-planner`, `implementation`, `receipts-54fz`, `diagnostics`, `integration-review`.
- MCP работает только через stdio.
- MCP предоставляет документацию, каталог API, офлайн-валидацию, объяснение ошибок и read-only диагностику тестового магазина.
- В MCP запрещены POST, PUT, PATCH и DELETE. Платежи, capture, cancel, refunds, receipts и webhook-настройки он не изменяет.
- Код write-интеграции создается в проекте пользователя и выполняется самим приложением с тестовыми реквизитами.
- Живая диагностика разрешена только после подтверждения `payment.test === true`.
- При `payment.test === false` производственные данные не возвращаются, а MCP блокируется до перезапуска.
- Расширение на боевые или финансовые операции требует отдельной версии, policy-слоя, human confirmation, аудита и новой модели угроз.

Эти ограничения текущего MVP имеют приоритет над более общей целевой архитектурой ниже.

## Язык работы

- Общение с пользователем, проектная документация и пояснения должны быть на русском языке.
- Имена программных сущностей, MCP-инструментов, функций, классов и файлов могут быть на английском, если это соответствует принятому стеку.
- Тексты ошибок для пользователя должны быть понятными на русском; внутренние коды ошибок должны быть стабильными и машиночитаемыми.

## Источники истины и их приоритет

При противоречиях использовать следующий порядок:

1. Действующее законодательство Российской Федерации и официальные разъяснения уполномоченных органов.
2. Актуальная официальная документация и OpenAPI-спецификация ЮKassa.
3. Фактическое поведение тестового API ЮKassa, если оно не противоречит источникам выше.
4. Локальные архитектурные решения, тесты и документация этого репозитория.
5. Документация Stripe как референс агентного интерфейса и мер безопасности.
6. Вторичные статьи, примеры и ответы сообществ — только как вспомогательный материал.

Нельзя использовать память модели или старый пример кода как подтверждение текущего поведения API, ставок НДС, состава чеков, требований ФФД или закона.

Перед изменением финансовой или фискальной логики агент обязан:

1. открыть актуальную документацию ЮKassa по затронутому сценарию;
2. проверить историю изменений API;
3. проверить актуальность требований 54-ФЗ и связанных нормативных актов;
4. зафиксировать использованные ссылки в PR, ADR или проектной документации;
5. явно отметить все неподтвержденные предположения.

### Что берем из подхода Stripe

- MCP как стандартный слой доступа агента к платежной системе.
- Разделение поиска метода API, получения его схемы, чтения и записи.
- Отдельный инструмент поиска по официальной документации.
- Отдельный planner, который сначала собирает требования, а затем рекомендует сценарий интеграции.
- Skills как версионируемые инструкции, дополняющие инструменты.
- OAuth для пользовательских подключений и минимально необходимые разрешения.
- Human confirmation для финансовых и иных рискованных изменений.
- Отдельные тестовый и боевой контуры.
- Минимальный контекст инструмента: не загружать всю спецификацию API в модель, если достаточно поиска операции и получения ее параметров.
- Защиту от prompt injection при совместном использовании нескольких источников и MCP-серверов.

### Что нельзя копировать из Stripe автоматически

- названия и состояния платежных объектов;
- модель PaymentIntent и другие Stripe-специфичные ресурсы;
- набор доступных платежных методов;
- схемы возвратов, автоплатежей, выплат и чеков;
- правила налогообложения и фискализации;
- способы аутентификации и модель разрешений без проверки возможностей ЮKassa;
- любые preview-возможности agentic commerce как уже доступные в ЮKassa.

## Нормативная база

Основной нормативный источник:

- [Федеральный закон от 22.05.2003 № 54-ФЗ «О применении контрольно-кассовой техники при осуществлении расчетов в Российской Федерации»](https://www.nalog.gov.ru/rn77/about_fts/docs/3909988/)

Ссылка ФНС ведет на полный текст на официальном портале правовой информации. Перед релизом и при изменении чековой логики необходимо проверять действующую редакцию закона, даты вступления изменений в силу, актуальный формат фискальных документов и официальные разъяснения ФНС.

54-ФЗ — обязательная, но не исчерпывающая часть правового контура. Если функция затрагивает персональные данные, переводы денежных средств, рекламу, дистанционную торговлю, маркировку, подписки или сохраненные способы оплаты, нужно отдельно определить применимость других норм. Агент не должен объявлять решение полностью соответствующим законодательству без юридической проверки.

## Границы продукта

### Входит в целевую архитектуру

1. MCP-сервер с четко описанными инструментами.
2. Клиент API ЮKassa, привязанный к актуальной OpenAPI-спецификации.
3. Поиск и получение документации ЮKassa.
4. Planner для выбора сценария интеграции.
5. Skills для типовых задач и правил безопасной разработки.
6. Авторизация, хранение секретов и разграничение полномочий.
7. Human-in-the-loop для рискованных операций.
8. Аудит вызовов и наблюдаемость без утечки чувствительных данных.
9. Тестовый контур, контрактные тесты и сценарии 54-ФЗ.

### Не считать готовым без отдельного подтверждения

- автономные платежи без участия человека;
- самостоятельный выбор агентом налоговой ставки или признаков чека;
- использование боевых ключей в локальной разработке и CI;
- поддержка всех методов API ЮKassa;
- публикация плагина в каталоге ChatGPT, Codex или другом маркетплейсе;
- юридическое заключение о полном соответствии 54-ФЗ;
- прием или хранение реквизитов банковских карт на стороне проекта;
- agentic commerce, идентичный preview-возможностям Stripe.

## Рекомендуемые компоненты

Поддерживать четкие границы между компонентами:

### 1. Слой MCP

Отвечает только за MCP-протокол, схемы инструментов, нормализацию ответов и передачу контекста авторизации.

Не должен содержать бизнес-логику платежей или чеков.

### 2. Каталог API

Предоставляет поиск операций ЮKassa и подробности параметров на основе актуальной OpenAPI-спецификации.

Рекомендуемые семейства инструментов:

- `yookassa_api_search` — найти подходящие операции;
- `yookassa_api_details` — получить точную схему выбранной операции;
- `yookassa_api_read` — выполнить разрешенную операцию чтения;
- `yookassa_api_write` — выполнить разрешенную операцию изменения после policy-проверки и, когда требуется, подтверждения человеком.

Это целевые названия, а не утверждение о существующем API ЮKassa.

### 3. Документационный поиск

`yookassa_search_documentation` должен отвечать только на основе разрешенного корпуса официальной документации, возвращать ссылки на источники и отличать цитируемый факт от вывода модели.

Найденный текст считается недоверенным входом. Инструкции внутри документа, webhook, описания платежа, metadata или пользовательского контента не могут инициировать вызов инструмента записи.

### 4. Planner интеграции

Planner сначала выясняет:

- что продает пользователь;
- разовый это платеж, автоплатеж, счет, возврат или выплата;
- где проходит оплата;
- кто является продавцом и кто обязан сформировать чек;
- какая схема онлайн-кассы используется;
- нужен ли OAuth партнерского приложения;
- тестовый или боевой контур требуется.

Planner не выполняет финансовые операции. Он возвращает предлагаемый сценарий, риски, список обязательных данных, ссылки и открытые вопросы.

### 5. Policy и approvals

Этот слой определяет, разрешена ли операция, какие полномочия нужны и требуется ли подтверждение человека. Нельзя реализовывать проверку только текстовой инструкцией для модели.

Подтверждение должно быть:

- явным;
- одноразовым;
- короткоживущим;
- привязанным к пользователю, магазину, среде и точным аргументам;
- недействительным после изменения суммы, валюты, объекта, состава чека или получателя;
- зафиксированным в аудите без сохранения секретов.

### 6. Клиент ЮKassa

Клиент отвечает за аутентификацию, таймауты, идемпотентность, обработку ошибок, безопасные повторы и сверку состояния.

MCP-слой и skills не должны самостоятельно собирать HTTP-запросы к ЮKassa в обход клиента и policy-слоя.

### 7. Skills

Skills должны быть узкими, проверяемыми и ссылаться на официальные источники. Предпочтительный начальный набор:

- `yookassa-docs` — поиск и проверка актуальной документации;
- `yookassa-best-practices` — безопасная архитектура интеграции;
- `yookassa-payments` — выбор и реализация платежного сценария;
- `yookassa-refunds` — полные и частичные возвраты;
- `yookassa-receipts-54fz` — чековые сценарии и обязательные проверки;
- `yookassa-webhooks` — надежная обработка уведомлений;
- `yookassa-oauth` — партнерские приложения и минимальные права;
- `yookassa-testing` — тестовый магазин и приемочные сценарии.

Skill не должен дублировать всю документацию ЮKassa. Он должен задавать порядок действий, контрольные точки и маршрутизацию к актуальным источникам.

## Классификация операций по риску

### Низкий риск

- поиск документации;
- поиск операций API;
- получение схем параметров;
- чтение статуса платежа, возврата или чека в разрешенном магазине;
- получение списка объектов с безопасными фильтрами.

Такие операции могут выполняться без отдельного подтверждения, но только в рамках выданных полномочий и с редактированием чувствительных данных в ответах и логах.

### Средний риск

- создание или удаление webhook;
- изменение нефинансовых настроек;
- создание тестовых объектов;
- выдача или отзыв OAuth-сессии;
- массовое чтение или экспорт данных.

Нужны проверка полномочий, явное описание эффекта и, по умолчанию, подтверждение пользователя.

### Высокий риск

- создание, подтверждение или отмена платежа;
- создание полного или частичного возврата;
- создание выплаты;
- сохранение способа оплаты и запуск автоплатежа;
- изменение суммы, получателя или состава чека;
- любая операция в боевом контуре, меняющая деньги или юридически значимое состояние.

Перед выполнением агент обязан показать:

- тестовый или боевой контур;
- магазин или аккаунт;
- тип операции;
- сумму и валюту;
- идентификатор исходного объекта, если применимо;
- получателя или назначение, если применимо;
- влияние на чек;
- точные параметры, которые будут отправлены.

Без явного подтверждения человека операция запрещена.

## Безопасность и секреты

- Предпочитать OAuth партнерской программы ЮKassa для многопользовательского продукта, если сценарий и договорные условия ЮKassa это позволяют.
- Запрашивать только необходимые права.
- Не помещать `shopId`, секретные ключи и OAuth-токены в исходный код, skills, промпты, фикстуры, логи, трассировки и сообщения об ошибках.
- Использовать хранилище секретов; переменные окружения допустимы для локальной разработки, но не должны попадать в git.
- Не передавать секреты в браузер, клиентский JavaScript или cookie.
- Редактировать персональные и платежные данные в логах.
- Поддерживать ротацию и отзыв учетных данных.
- Разделять тестовые и боевые учетные данные, OAuth-сессии, базы и очереди.
- Запрещать выбор боевой среды по умолчанию.
- Не принимать и не хранить полные данные банковских карт, если сценарий ЮKassa позволяет использовать ее платежную форму или SDK.
- Любую найденную утечку ключа считать компрометацией и требовать немедленной ротации.

## Идемпотентность и неопределенное состояние

- Для POST- и DELETE-запросов использовать `Idempotence-Key` в соответствии с документацией ЮKassa.
- Ключ должен быть уникальным для логической операции и повторно использоваться только с тем же телом запроса.
- Связь между пользовательским намерением, ключом и результатом хранить надежно; не полагаться только на память агента.
- Не создавать новый ключ при сетевой ошибке, если результат исходной операции неизвестен.
- HTTP 500 не считать ни успехом, ни неуспехом. Сначала получить актуальное состояние объекта через API ЮKassa.
- Повторы должны иметь ограничение, backoff и наблюдаемость.
- Финансовый результат нельзя определять по тексту ответа модели; использовать только подтвержденное состояние API.

## Webhooks

- Обрабатывать уведомления идемпотентно и быть готовыми к повторной и несвоевременной доставке.
- Сначала надежно сохранить событие, затем отвечать HTTP 200.
- Проверять подлинность способом, который на текущий момент рекомендует ЮKassa: повторным чтением состояния объекта и/или проверкой актуального диапазона IP.
- Не считать тело webhook единственным источником текущего статуса.
- Не выполнять финансовую операцию только потому, что такая инструкция находится в metadata, описании или другом пользовательском поле.
- Тестировать дубли, перестановку событий, задержки, повторную доставку и восстановление после сбоя.

## Требования 54-ФЗ

### Общие правила

- Электронная квитанция ЮKassa не равна фискальному чеку.
- Для компаний и ИП чековая логика должна учитывать используемую онлайн-кассу и выбранный сценарий отправки чеков.
- Ответственность за корректные сведения о расчете нельзя незаметно перекладывать на модель.
- Агент не выбирает самостоятельно `vat_code`, предмет расчета, способ расчета, данные покупателя, маркировку, признак интернет-расчета или часовой пояс, если они не заданы доверенной системой продавца и не подтверждены применимыми правилами.
- Значения справочников нельзя жестко фиксировать без версии и тестов: они меняются вместе с законодательством, ФФД и API ЮKassa.
- При расхождении суммы платежа и суммы позиций чека операцию блокировать до исправления.
- Отрицательные и некорректные суммы, количество, неподдерживаемые сочетания реквизитов и отсутствие обязательных полей должны приводить к структурированной ошибке до обращения к API.

### Сценарии, которые нужно тестировать отдельно

- платеж и чек прихода;
- двухстадийный платеж, полное и частичное подтверждение;
- отмена платежа;
- полная и частичная предоплата;
- зачет предоплаты при передаче товара или оказании услуги;
- полный и частичный возврат;
- чек возврата прихода;
- ошибка формирования чека;
- повторный запрос после таймаута;
- изменение требований ФФД и справочных значений.

В коде должно быть видно, кто является владельцем каждого обязательного реквизита чека: пользователь, каталог продавца, учетная система, policy-конфигурация или ответ ЮKassa. Модель не является источником юридически значимых реквизитов.

## Работа с ошибками

Инструменты должны возвращать структурированные ошибки как минимум с полями:

- стабильный внутренний код;
- безопасное сообщение пользователю;
- тип ошибки: validation, authorization, policy, confirmation, transport, API, fiscalization или unknown_state;
- возможность безопасного повтора;
- идентификатор корреляции;
- ссылка на документацию, если она помогает устранить ошибку.

Не показывать секреты и необработанное тело внешней ошибки. Не советовать повтор финансовой операции, пока не исключено неопределенное состояние.

## Тестирование

### Обязательные уровни

1. Unit-тесты преобразований, валидации и policy-решений.
2. Контрактные тесты клиента по актуальной OpenAPI-спецификации ЮKassa.
3. Golden-тесты схем MCP-инструментов.
4. Тесты approval-токенов и защиты от подмены аргументов.
5. Тесты prompt injection и недоверенных данных.
6. Интеграционные тесты с тестовым магазином ЮKassa.
7. Приемочные сценарии платежей, возвратов, webhooks и чеков.

### Минимальные негативные сценарии

- повтор одного запроса и двойная отправка;
- новый payload со старым ключом идемпотентности;
- таймаут и HTTP 500 с неизвестным результатом;
- повторный и устаревший webhook;
- webhook с поддельным содержимым;
- попытка изменить подтвержденную сумму;
- попытка перейти из тестовой среды в боевую;
- отсутствие или превышение OAuth-права;
- несовпадение суммы платежа и чека;
- отсутствующий или неподдерживаемый реквизит 54-ФЗ;
- секрет в логе, трассировке или ответе инструмента.

Автоматические тесты не должны выполнять реальные списания, возвраты или выплаты.

## Рабочий процесс агента

Перед началом изменения:

1. прочитать этот файл и более локальные `AGENTS.md`, если они появятся;
2. изучить существующие файлы, README, манифесты и тесты;
3. проверить `git status` и не затрагивать чужие изменения;
4. определить источник истины для изменяемого поведения;
5. сформулировать границы и риски изменения;
6. для юридически или финансово значимой логики проверить актуальные внешние источники.

Во время изменения:

- делать минимальные и сфокусированные правки;
- не добавлять зависимость без обоснования необходимости и проверки сопровождения;
- использовать существующий менеджер пакетов и lock-файл;
- отделять транспорт, доменную логику, policy и представление инструментов;
- не скрывать неподтвержденные предположения;
- не ослаблять проверки ради прохождения тестов.

После изменения:

1. запустить относящиеся к изменению тесты и статические проверки;
2. проверить отсутствие секретов и персональных данных;
3. проверить тестовый/боевой контур;
4. перечислить измененное поведение, проведенные проверки и оставшиеся риски;
5. для финансовой или фискальной логики указать использованные официальные источники и дату проверки.

## Критерии готовности функции

Функция не готова, пока:

- ее поведение не подтверждено актуальной документацией ЮKassa;
- права доступа не минимизированы;
- операции изменения не проходят через policy-слой;
- рискованные операции не требуют корректного human confirmation;
- идемпотентность и неопределенное состояние не протестированы;
- чувствительные данные могут попасть в логи или ответы;
- отсутствуют негативные тесты;
- чековый сценарий не проверен на требования 54-ФЗ, если функция влияет на расчет;
- нет понятного сообщения об ошибке и безопасного пути восстановления;
- тестовая и боевая среды могут быть перепутаны.

## Принцип принятия решений

Если данных недостаточно, агент должен остановить рискованную операцию и запросить недостающие сведения. В финансовых и фискальных сценариях безопасный отказ предпочтительнее догадки.

Нельзя принимать решения без подтверждающих данных.

# Диагностика тестового магазина ЮKassa

## Safety gate

1. Убедись, что пользователь намерен проверить тестовый магазин.
2. Не проси вставлять shopId или secret key в чат. Они должны быть локальными переменными `YOOKASSA_SHOP_ID` и `YOOKASSA_SECRET_KEY`.
3. Первым живым вызовом всегда используй `yookassa_diagnose_connection`.
4. Продолжай только при `testMode: confirmed`.
5. При `testMode: unconfirmed` попроси создать один тестовый платеж кодом приложения и повторить диагностику.
6. При `PRODUCTION_STORE_BLOCKED` останови все живые вызовы, объясни замену реквизитов и необходимость перезапуска Codex.

## Диагностическое дерево

- Ошибка соединения: вызови `yookassa_explain_error`, проверь Basic Auth, совпадение shopId/key, сетевой доступ и права.
- Неожиданный платеж: получи его через `yookassa_get_payment`, сравни статус, сумму, валюту, payment method, cancellation details и внутреннее состояние заказа.
- Список событий: используй `yookassa_list_payments` с минимальным limit и узким фильтром времени/статуса.
- Возврат: вызови `yookassa_get_refund`; инструмент сам проверит связанный платеж с `test=true`.
- Чек: вызови `yookassa_get_receipt`; сравни тип, статус, позиции, НДС, сумму и связь с платежом/возвратом.
- Сохраненный способ: доступен через `yookassa_get_payment_method` только после подтверждения тестового магазина.
- Ошибка будущего POST: используй `yookassa_validate_request`, не отправляя запрос.
- Неясный метод: используй `yookassa_api_search` и `yookassa_api_details`.

## Диагностика webhook

MCP не получает настройки webhook магазина. Проверь код и логи приложения:

- URL публично доступен по HTTPS;
- обработчик быстро отвечает HTTP 200;
- событие может прийти повторно;
- статус повторно проверяется через API;
- переход состояния идемпотентен;
- тестовый URL отделен от production;
- redirect пользователя не заменяет webhook/API-проверку.

## Отчет

Сформируй:

- подтвержденную среду и safety status;
- симптомы и временной диапазон;
- выполненные read-only проверки;
- фактические статусы и связи объектов;
- наиболее вероятную причину с доказательствами;
- безопасный следующий шаг;
- что нельзя подтвердить имеющимися данными;
- команды/тесты после исправления.

Не возвращай исходные API-ответы с PII. Используй минимизированные результаты инструментов и `references/checklist.md`.

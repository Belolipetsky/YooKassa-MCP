# Реализация интеграции ЮKassa

## Обязательный порядок

1. Прочитай правила репозитория и выясни язык, фреймворк, package manager, тестовый стек, ORM и текущую платежную архитектуру.
2. Найди существующие модели заказа/платежа, HTTP-клиент, secret management, webhook routes и фоновые задачи. Не создавай параллельный слой без причины.
3. Получи актуальные операции через `yookassa_api_search` и `yookassa_api_details`; открой официальные документы из `yookassa_search_documentation`.
4. Сначала напиши тест на требуемое поведение и проверь, что он падает по ожидаемой причине.
5. Реализуй минимальный вертикальный сценарий в стиле проекта.
6. Перед сетевым тестом проверь будущий POST через `yookassa_validate_request`. MCP не должен выполнять этот POST: его выполняет код приложения с тестовыми реквизитами.
7. Запусти unit/contract тесты. Живую диагностику начинай с `yookassa_diagnose_connection` и продолжай только после `testMode: confirmed`.
8. Покажи измененные файлы, проверки и оставшиеся допущения.

## Инварианты реализации

- API вызывается только с доверенного сервера по HTTPS.
- `YOOKASSA_SECRET_KEY` приходит из secret storage/environment и никогда не логируется.
- Каждый POST получает стабильный `Idempotence-Key` до первого запроса; ключ и результат сохраняются атомарно с бизнес-операцией.
- Timeout и retry ограничены. Повтор POST для одной операции не создает новый ключ.
- Суммы хранятся в минимальных денежных единицах или точном decimal-типе; float запрещен.
- Внутренний заказ хранит `payment_id`, `refund_id`, статусы и историю переходов.
- Redirect пользователя не считается доказательством оплаты.
- Webhook может повторяться и приходить не по порядку. Обработчик повторно получает объект через API и применяет только допустимый идемпотентный переход.
- Пользовательские metadata не должны содержать секреты и лишние персональные данные.
- Валидация запроса и бизнес-правила выполняются до API-вызова.

## Чеки

Если сценарий затрагивает фискализацию, дополнительно примени skill `receipts-54fz`. Не выбирай `vat_code`, `payment_subject`, `payment_mode`, систему налогообложения или требования маркировки без подтвержденных данных.

## Проверка результата

Минимально проверь:

- успешный сценарий тестового платежа;
- повтор запроса с тем же ключом;
- сетевой timeout;
- повторный webhook;
- неожиданный порядок статусов;
- 401, 403, 404, 422, 429 и 5xx;
- полное и частичное действие, если оно входит в scope;
- совпадение суммы и валюты заказа с объектом ЮKassa;
- отсутствие секретов и PII в логах/ошибках.

Чек-лист файлов и тестов находится в `references/checklist.md`.
